After this milestone, each statement about the compatibility of Randoc comes
from a scoreboard row. Each metric key of `plan/SPEC.md` has a working
measurement with an exact PASS and TOTAL, the gate passes inside the build
sandbox, the first held-out result of a clean commit exists, and a clean
baseline of all metrics exists. The later milestones then move numbers that
mean something.

The first command exits 0 and prints each requirement of M1 as met. The
second shows a row for each metric key and no open counter limit.

## Context and Orientation

The repository is `/Volumes/Extreme Pro/Randoc/gpt/randoc`, branch
`gpt/build`. Randoc is a Rust workspace (`crates/randoc-*`). The oracle is
Pandoc 3.13 at `$RANDOC_ORACLE_PANDOC`. The rules of the work are in
`AGENTS.md`.

Terms:

- **Unit**: one comparison of Randoc with the oracle: same input and
  options, compare exit code, standard error and output (`plan/SPEC.md` 3).
- **Metric**: PASS/TOTAL of a set of units, with a key such as `lua.api`.
- **Row**: one metric of one measurement run in `plan/scoreboard/*.tsv`.
- **Suite**: a group of metrics that one command measures.
- **Runner**: the code in `measure.py` (or in `tools/autobuild/suites/`) that
  reads the raw output of a suite and returns the units.
- **Evidence**: the raw output of a run, in
  `/Volumes/Extreme Pro/Randoc/gpt/runs/measure/<utc>-<sha>/`.
- **Oracle cache**: stored oracle results outside the repository,
  `$RANDOC_GPT/cache/SUITE/` (`plan/SPEC.md` 4.4).
- **Pivot set P**: 400 JSON document trees from an own generator
  (`plan/SPEC.md` 4.2); each writer converts each tree.
- **Data pack**: Pandoc's data files that the licence keeps out of the
  repository, made from the oracle by a tool, in `$RANDOC_GPT/datapack`
  (`plan/ARCHITECTURE.md` 4.7).

Key files:

- `tools/autobuild/ops` - the operations command (`ops status` first).
- `tools/autobuild/measure.py` - runs suites and writes rows.
  `tools/autobuild/metrics.toml` - the registry of metrics (status `active`,
  `to-build` or `external`).
- `tools/autobuild/suites/README.md` - how a new suite is added as new files.
- `tools/autobuild/gate.py` - the gate.
- `crates/randoc-harness/` and `conformance/` - the differential harness

- `tools/pandoc-testsuite/` - runs Pandoc's tests from `env/pandoc-src/test`.
- `tools/corpus/` - the corpus of real documents.
- `tools/casegen/` - generated cases (visible seeds 1 to 1000).
- `spec/inventory/` - the lists of formats, extensions and options from the

## Plan of Work

The work has three phases. Phase A and B change shared tools, so the lead
does them on `gpt/build`. Phase C has independent items for workers.

**How a new measurement is added (each item of phase B and C).** Write the
tool under `tools/<name>/` (Python 3.11 or later, standard library), with
unit tests. It runs both programs, or reads stored oracle results from the
oracle cache, and writes raw output into the evidence folder. Add the
runner as `tools/autobuild/suites/<name>.py` and the metric entries as
`tools/autobuild/metrics.d/<name>.toml` (`tools/autobuild/suites/README.md`
gives the form). A `metrics.d` entry replaces the `to-build` entry of the
same key. Follow `plan/SPEC.md` section 5 for the unit, PASS and TOTAL of
the key, section 3.10 for unstable units, 3.11 for excluded units, 4.4 for
results that hold copyleft text, and 8 for the licence. Each oracle run gets
`GHCRTS=-M3g`; an oracle exit 251 is "no result", never a result. Test the
tool inside the sandbox. Then run `ops measure --item ID --quick` (or
`--suite NAME`) to get the first row.

**Phase A (lead, in this order).**

A1. Run `ops measure` on the newest clean commit and commit the rows. Make
the first real held-out request (`ops holdout request`).

A2. M1-01 (active). Make `gate.steps` a metric: `gate.py` writes one unit for
each step that `plan/SPEC.md`, section `gate.steps`, lists, plus these
self-checks: a stand-in oracle (a small script on `PATH` that records its
environment) shows that each tool that runs the oracle passes
`GHCRTS=-M3g`; the SHA-256 of the oracle equals `plan/SPEC.md` 1; a scan of
`crates/` shows that Randoc never runs the oracle. Add a suite `gate` with
the key `gate.steps`. Replace the 20 s wall-time limit of a harness unit in
`crates/randoc-harness/src/exec.rs` with a CPU-time limit of the child
(`getrusage` of the children, or `proc_pid_rusage`), and keep a larger wall
limit for a hang. Check that `./init.sh --quick` runs inside the sandbox; if
the hook copy fails, make `init.sh` skip the copy when `core.hooksPath` is
set (the guard is the active hook).

A3. M1-02. Add the seeded-regression self-checks: for each baseline check
(harness, Pandoc's suite, corpus), a stand-in Randoc that breaks one passing
unit must make the check fail. Each check is one unit of `gate.steps`.

**Phase B (lead, in this order).**

B1. M1-03. Extend the harness so that a case can name output files
(`-o FILE`, `--log FILE`, `--extract-media DIR`); the harness runs each
program in its own empty temporary folder, collects each written file, and
compares it by the rules of `plan/SPEC.md` 3 (ZIP by content, text by
bytes). Add at least 60 cases. Key `files.units`.

B2. M1-04. Write the generator `tools/pivot/` for the pivot set P (`plan/SPEC.md`
4.2), store the SHA-256 of its list in `spec/pivot.sha256`, and add a suite
that converts each tree of P with each writer (76 keys `fmt.write.F` and the
sum `fmt.write`). Oracle results that embed copyleft text stay in the oracle
cache. Then apply the strict rule of `caps.writers` (tool correction,
`decision` entry).

B3. M1-05. Add the reader inputs of `plan/SPEC.md`, section `fmt.read.F`
(the oracle's output of P in each format that is also a writer, the own
case inputs, the visible corpus documents of the format), and a suite with
the 52 keys `fmt.read.F` and the sum `fmt.read`. For the 12 readers that are
not writers, write 40 or more own inputs each (`plan/ROADMAP.md`, "Metric
keys that this roadmap adds"). Then apply the strict rule of `caps.readers`.

**Phase C (workers; up to 4 at a time; any order).** Each item adds one tool
and its suite files. They do not depend on each other, except where noted.

- M1-06 `caps.extensions`: one sensitive probe set (`plan/SPEC.md` 4.3) for
  each (direction, format, extension) pair of `spec/inventory/`; TOTAL 1,719.
- M1-07 `caps.options`: value sets for each option on 5 base conversions;
  short options map to long names; strict rule of `caps.options`.
- M1-08 `ast.roundtrip`: JSON and `native` round trip of each distinct
  oracle tree; each wrong `pandoc-api-version` form.
- M1-09 `templates.units`: variable sets and documents for each format with
  a default template; user partials.
- M1-10 `defaults.units`: one unit for each defaults-file key that the
  oracle accepts.
- M1-11 `errors.units`: one confirmed trigger for each exit code; the
  `--verbose` and `--log` output of the corpus and pivot conversions.
- M1-12 `lua.api`: call probes for each of the 468 names of the `pandoc` Lua
  module, run as a filter that prints the results.
- M1-13 `lua.filters`: a matrix of element type, return kind, traversal
  order and filter form on the pivot set.
- M1-14 `custom.readers` and M1-15 `custom.writers`: 10 own-written custom
  readers and 10 custom writers (new form, classic form, `Template`,
  `Extensions`).
- M1-16 `suite.pandoc.lua`: run the Lua test files of
  `env/pandoc-src/pandoc-lua-engine/test` at run time (never commit them).
- M1-17 `suite.pandoc.inline`: read the input strings of the Haskell-only
  test groups of `env/pandoc-src/test` at run time; tests that cannot be
  mapped go to a `not_extracted` list with a reason (`plan/SPEC.md`).
- M1-18 `citeproc.units`: styles, bibliography formats, the citation matrix
  and 4 output formats; styles are fetched into the data pack, never
  committed.
- M1-19 `zip.units`: the data pack tool `tools/autobuild/datapack` (needed
  by M1-09, M1-18 and M1-20 for files from the data pack; do it early); an
  oracle self-check that lists the archive entries that differ between two
  oracle runs.
- M1-20 `pdf.units`: a recording stand-in for each PDF engine and the
  "engine missing" case for each engine.
- M1-21 `perf.throughput`, `perf.startup`, `perf.memory`: speed, start time
  and peak memory against the oracle for each corpus document, in one run.
- M1-22 `safety.units`: generated stress inputs for each reader and writer
  that exists, under `limit-run`; TOTAL 100 or more.
- M1-23 `server.units`: requests to the oracle server on a local port.
- M1-24 `lib.units` and `wasm.units`: a small command on the library API
  with a pure host; `wasm.units` stays 0 until a WebAssembly build exists.
- M1-25 `downstream.quarto` and `downstream.rmarkdown`: sample projects with
  open licences; record each call of the oracle and replay it with both
  programs. Quarto and R are not installed: write the rows as 0/TOTAL and an
  entry with `ops blocked`.
- M1-26 `casegen.visible` and the three family keys: run the visible
  generated cases (seeds 1 to 1000, `--count 2` each, `plan/SPEC.md`).

## Idempotence and Recovery

A measurement only appends rows; running it again is safe. A failed or
stopped measurement writes no row for the suites that did not end. A gate run
can be repeated at any time; it changes no file of the repository. An item
that shows no gain in 3 experiments is cut with `ops item cut`, which reverts
its commits in one new commit. A worker that fails is removed with
`ops worker drop`; its branch stays for the review. If a new tool changes the
TOTAL of an existing metric, measure the previous commit again with the new
tool before you compare (`plan/SPEC.md` 3.13), and write a `decision` entry.
