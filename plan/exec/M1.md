## Purpose / Big Picture

After this milestone, each statement about the compatibility of Randoc comes
from a scoreboard row. Each metric key of `plan/SPEC.md` (except
`install.units`, which M8 builds) has a working measurement with an exact
PASS and TOTAL, the gate passes inside the build sandbox, a held-out result
of the final clean commit exists, and a clean baseline of all metrics
exists. The later milestones then move numbers that mean something.

To see it work, run from the repository root:

    . tools/autobuild/env.sh
    tools/autobuild/ops milestone check M1
    tools/autobuild/ops status

The first command exits 0 and prints each requirement of M1 as met. The
second shows a row for each metric key and no open counter limit.

## Context and Orientation

The repository is `/Volumes/Extreme Pro/Randoc/gpt/randoc`, branch
`gpt/build`. Randoc is a Rust workspace (`crates/randoc-*`). The oracle is
Pandoc 3.13 at `$RANDOC_ORACLE_PANDOC`. The rules of the work are in
`AGENTS.md`.

Terms:

- **Unit**: one comparison of Randoc with the oracle: same input and
  options, compare exit code, standard error and output (`plan/SPEC.md` 3).
- **Metric**: PASS/TOTAL of a set of units, with a key such as `lua.api`.
- **Row**: one metric of one measurement run in `plan/scoreboard/*.tsv`.
- **Suite**: a group of metrics that one command measures.
- **Runner**: the code in `measure.py` (or in `tools/autobuild/suites/`) that
  reads the raw output of a suite and returns the units.
- **Evidence**: the raw output of a run, in
  `/Volumes/Extreme Pro/Randoc/gpt/runs/measure/<utc>-<sha>/`.
- **Experiment**: one `ops measure --item ID` run. It writes an attempt
  record in `/Volumes/Extreme Pro/Randoc/gpt/runs/attempts.tsv` before it
  starts, so a failed run also counts.
- **Tool correction**: a recorded change of how a tool counts the units of
  a metric: `ops correction add METRIC --item ID --reason TEXT`, a row in
  `plan/corrections.tsv` (`plan/SPEC.md` 3.13).
- **Candidate run**: the full measurement that `ops milestone check` uses
  (`plan/SPEC.md` 4.1).
- **Broker**: the owner's support program outside the sandbox. It pushes
  (`ops push`), starts review and adviser sessions, and builds the commit of
  a held-out request.
- **Oracle cache**: stored oracle results outside the repository,
  `$RANDOC_GPT/cache/SUITE/` (`plan/SPEC.md` 4.4).
- **Pivot set P**: 400 JSON document trees from an own generator
  (`plan/SPEC.md` 4.2); each writer converts each tree.
- **Data pack**: Pandoc's data files that the licence keeps out of the
  repository, made from the oracle by a tool, in `$RANDOC_GPT/datapack`
  (`plan/ARCHITECTURE.md` 4.7).

Key files:

## Plan of Work

The work has three phases. Phase A and B change shared tools or existing
metrics, so the lead does them on `gpt/build`, one item at a time. Phase C
has independent items for workers. Phase C starts when M1-04 is done,
because most of its items use the pivot set P.

**How a new measurement is added (each item of phase B and C).** Write the
tool under `tools/<name>/` (Python 3.11 or later, standard library), with
unit tests. It runs both programs, or reads stored oracle results from the
oracle cache, and writes raw output into the evidence folder. Add the
runner as `tools/autobuild/suites/<name>.py`, the metric entries as
`tools/autobuild/metrics.d/<name>.toml` and the tests as
`tools/autobuild/tests/test_suite_<name>.py`
(`tools/autobuild/suites/README.md` gives the form). A `metrics.d` entry
replaces the `to-build` entry of the same key. Follow `plan/SPEC.md`
section 5 for the unit, PASS and TOTAL of the key, section 3.10 for unstable
units, 3.11 for excluded units and for oracle failures, 4.4 for results
that hold copyleft text, and 8 for the licence. Each oracle run gets
`GHCRTS=-M3g`; an oracle exit 251 is "no result", never a result. A unit
that cannot run (a missing program or build) fails; its metric keeps its
full TOTAL. Test the tool inside the sandbox. When the suite files exist,
run the first experiment: `ops measure --item ID --suite NAME`. Before that,
run no experiment of the item.

## Concrete Steps

Run each command from `/Volumes/Extreme Pro/Randoc/gpt/randoc`.

Session start:

    . tools/autobuild/env.sh
    tools/autobuild/ops status

One item (the lead):

    tools/autobuild/ops item start M1-03
    # change, test, commit with [M1-03] at the end of the subject
    tools/autobuild/ops measure --item M1-03 --suite NAME
    tools/autobuild/ops gate

NAME is the suite of the item's metric. An item that fixes product code
uses `--quick` in place of `--suite NAME`; `ops status` names the right
command. Run the gate before `ops item done`; if the gate fails, the item
stays active. `ops item done` refuses without a passing full gate of the
current commit: a gate on a tree with no change outside `plan/`, of `HEAD`
or of a commit whose diff to `HEAD` changes only `plan/`.

An item whose title gives a coverage rule holds it in the column `accept`

milestone check tests the exact TOTAL. A latest row that does not meet the
rule is no gain for the guard, `ops` and `measure.py`: three experiments with
no such row (for example only `0/N` for an `all-pass` item) exhaust the
item, and only a cut is left. A new item gets its rule with
`ops item add --all-pass` or `--min-total N`.

    tools/autobuild/ops correction add caps.writers --item M1-04 --reason "strict rule of plan/SPEC.md"
    tools/autobuild/ops log decision --item M1-04 "old and new rule, old and new TOTAL, removed units"

change, measure and request again.

## Idempotence and Recovery

A measurement only appends rows; running it again is safe. A failed or
stopped measurement writes no row for the suites that did not end, but its
attempt record stays: it counts as an experiment of the item. A gate run
can be repeated at any time; it changes no file of the repository. An item
that shows no gain in 3 experiments is cut with `ops item cut`, which
reverts its commits in one new commit and withdraws its tool corrections
(the rows from the correction to the cut no longer count; the older rows
count again). A worker that fails is removed with
`ops worker drop`; its branch stays for the review, and the command refuses
a worktree with changes. If a new tool rule changes PASS or TOTAL of an
existing metric, record a tool correction before the first row with the
new rule (`plan/SPEC.md` 3.13); do not measure an old commit again.
